# The remote-compile std-fd bug (fixed on virtu-fdfix)

Date: 2026-10-05.  Branch `virtu-fdfix` (off `c8bb615f`), unpushed, pending
review.  The customer-visible symptom: on the worker image, a remote
compile job dies instantly -- the compiler child exits 1 with nothing on
stdout/stderr.  Root cause, verified twice over (code read + exec-state
strace decode, and the two regression tests below):

## Root cause

`iceccd` can be started with fds 1 and 2 closed (a container start or a
supervisor closing its own std fds before exec).  Every descriptor the
daemon then opens squats onto the closed slots, and `pipe()` allocates the
LOWEST free descriptors -- so in `workit`, forked per job, the pipe pairs
land exactly on the std numbers.  In the classic child-side setup sequence
(`daemon/workit.cpp:410-457`):

```
close(sock_out[0]); dup2(sock_out[1], STDOUT); close(sock_out[1]);
close(sock_err[0]); dup2(sock_err[1], STDERR); close(sock_err[1]);
close(sock_in[1]);  dup2(sock_in[0], STDIN);   close(sock_in[0]);
```

with `sock_err == (1, 2)` (the squatted layout) the sequence
self-clobbers: `close(sock_err[0])` closes the stdout `dup2(sock_out[1], 1)`
just installed, `dup2(2, 2)` is a documented self-no-op, and
`close(sock_err[1])` closes stderr outright.  The compiler is exec'd with
fds 1/2 closed; in the job chroot, whose environment tarball has no
`/dev/null` (character-device extraction is skipped without CAP_MKNOD),
LLVM's `FixupStandardFileDescriptors()` tries to open `/dev/null` for 1/2,
gets ENOENT, and exits 1 instantly.  gcc children are unaffected (no such
fixup), which is why the bug is clang-shaped.

The pre-fix daemon-side fd state, verified by strace on the real binary:
`static ofstream logfile_null("/dev/null")` in `services/logging.cpp:44`
is a static initializer that runs BEFORE `main()` and accidentally re-fills
a closed fd 1 slot (`openat("/dev/null", O_WRONLY|O_CREAT|O_TRUNC) = 1`
ahead of `getpid()`), so fd 2 is the discriminating slot at the daemon
level: left closed, it is then squatted by the daemon's own unix listener
socket (`bind()` lands the socket on fd 2).  The daemon-level regression
below observes exactly that: at `c8bb615f` fd 2 readlinks to
`socket:[...]`; with the fix it readlinks to `/dev/null`.

## The fix (three layers)

1. **Startup sanitize** (`services/fd_guards.h`, called first thing in
   `main()` before any open/socket/pipe, from `daemon/main.cpp`):
   `sanitize_standard_fds()` re-opens host-fs `/dev/null` onto any closed fd
   among 0/1/2 (O_RDWR; never touches an already-open std fd; POSIX-close,
   before any chroot could hide /dev/null).  A daemon that starts healthy
   never even reaches the open().
2. **Job-child sanitize** (`daemon/serve.cpp`, post fd-hygiene sweep,
   pre-chroot, defence in depth): if /dev/null is unavailable before the
   environment transition the child dies loudly instead of exec-ing a
   compiler with closed std fds.
3. **Squat-proof workit** (`daemon/workit.cpp`, the belt to 1's braces):
   after the five pipe pairs exist, `move_pipe_ends_off_standard_fds()`
   (`services/fd_guards.h`) moves any pipe end that squatted a std slot to
   a descriptor >= 3 (F_DUPFD) BEFORE the child-side dup2/close sequence
   runs -- so the sequence is correct regardless of the fd state workit
   inherited, including when forked from a legacy (pre-fix) daemon.

The sidecar inherits open std fds from the sanitized daemon (a child of a
process whose 0/1/2 are open cannot have them closed unless it closes
them itself), so the startup sanitize covers it.

## Regression tests (workit/daemon: RED at c8bb615f, GREEN at virtu-fdfix; sidecar: GREEN-only)

**Sidecar leg** (`unittests/stdfdsanitize-sidecar.sh`, GREEN-only): starts a
scheduler plus the production-shaped daemon (root-started, capng drop to
icecc, `--cache-service` + `--cache-runtime-dir` with the runtime dir
pre-chowned icecc:icecc 0700 -- the adapter's `valid_config`/`private_
directory` rejects anything else) with 1/2 closed, waits for the exec'd
`icecc-cache-service` child (selected by ppid: a plain pgrep -f matches the
daemon's own `--cache-service` argv and the test script itself), and
asserts the service's 0/1/2 are open, `/dev/null` or a real inherited
stream, never a socket or pipe.  The adapter child itself never touches
0/1/2 (`cache/p50_daemon_sidecar_adapter.cpp`: closes only its own owned
fds, `close_range(3,..)` is CLOEXEC-only), so the service's std fds are the
daemon's, verbatim.  At c8bb615f this leg PASSES TOO -- and that is the
honest expected outcome, not a test failure: the pre-fix service child's
std-fd state is timing-dependent (the daemon's fd 2 is a revolving door of
transient opens -- capng status reads, probe sockets -- and the service's
own static `logfile_null("/dev/null")` init re-fills whichever std slot
happened to be closed at its exec, masking whatever it inherited; a trace
at c8bb615f shows `openat("/dev/null", ..., O_TRUNC) = 2` INSIDE the
service child's own static init).  With the fix the daemon pins 0/1/2 open
before anything else runs, so the service's inheritance is deterministic --
that determinism is what the leg locks in.

**Workit-level, farm-free** (`unittests/stdfdworkit.cpp`): forks with 1/2
closed, creates the five workit pipe pairs, runs the verbatim child-side
sequence, execs `/bin/sh` as the stand-in compiler which reports its own
0/1/2 open-ness over a side report pipe the sequence never touches.  The
same source compiles at `c8bb615f` (`__has_include`): fd_guards.h does not
exist there, the relocation call compiles out, and the legacy squatted
sequence runs -- the RED leg.  Verified on H2 (icecream-builder:vfos6
container): RED fails "helper was exec'd with a closed std fd (sequence
self-clobber)", GREEN passes "helper exec'd with 0/1/2 open, relocation
active".

**Daemon-level** (`unittests/stdfdsanitize-run.sh`): starts the REAL
iceccd with 1/2 closed via an exec-helper; the test re-execs itself as the
icecc user (same-uid `/proc/<pid>/fd` probes -- container-root readlink of
an icecc-owned fd table is EPERM without CAP_SYS_PTRACE) and pins HOME to
the workdir (the unix-listener bind at `$HOME/.iceccd.socket` is fatal for
a non-root uid whose HOME is not writable -- an inherited HOME=/root exits
1 at the bind with nothing to do with the fd bug).  Asserts 0/1/2 exist in
`/proc/<pid>/fd`, that fd 1/2 are `/dev/null` (not a squatted socket/pipe),
and that at least one fd >= 3 exists (the listener -- proving the daemon's
own descriptors found free slots above std).  Verified on H2: RED at
`c8bb615f` fails "fd 2 is not /dev/null: socket:[...]" (the listener
squatting the closed std slot); GREEN passes "daemon keeps 0/1/2 open when
started with 1/2 closed".

## How it shipped (the QA gap, corrected)

The first account ("release QA never ran the hygiene suite") was WRONG:
the official `make qa` runs (H4, 09-26/09-27/09-29) show
`PASS: p50forkfdhygiene` (plus the -source/-mutants/-oot variants) --
`dev/bootstrap.py` passes `--cap-add SYS_PTRACE` in qa mode, so kcmp was
allowed and the suite RAN.  The whole-binary SKIP exists, but it came from
harnesses without SYS_PTRACE (the k310 agent's own runs), not release QA.
The real gap is worse: **QA tested a different binary from the one we
ship.**  Release QA builds in the ubuntu24.04 SDK, whose headers define
`SYS_close_range` -- so QA's hygiene suite ran the `close_range` backend,
and `proc_fallback` only ever executed under injected failures, with
nothing asserting std fds there.  The f28 headers of the node image and
the VFOS5 rpm compile `close_range_sweep` into a stub, so EVERY shipped
job child ran the unbounded `proc_fallback` -- a path release QA never
exercised end to end.  Compounding it: the six end-to-end
remote-compile tests (`remoteice-quick.sh`, `p50assignment-remote.sh`,
`p50sourcearm-live-run.sh`, `p50daemonpositive-run.sh`,
`p50compilee2e-run.sh`, `p50completionflow-run.sh`) SKIPped in release QA
(needing a root container with CAP_SYS_CHROOT, opt-in env vars, or a
non-loopback IP), so **no real remote compile ever ran in QA against the
shipped shape** -- and the only remote compile that did run (the gcc
image smoke) could not catch the class, because gcc ignores closed std
fds while clang dies in a dev-less chroot.

Closures on virtu-fdfix (all unpushed): the per-case kcmp skip table +
`dev/seccomp-kcmp.json` (docker default + unconditional kcmp) so the
hygiene suite cannot silently skip in QA again;
`configure --enable-qa-force-proc-sweep` + run-qa.sh's `native-proc-check`
stage so the proc backend is exercised suite-wide against a
close_range-compiled-out build (the cheap test-what-we-ship variant; the
full variant is an f28-SDK QA leg); and icecream_builder's
`scheduler/smoke-clang-nodev.sh` (run by `scheduler/build.sh` after the
gcc smoke) -- one remote clang compile through a create-env env WITHOUT
/dev/null, asserting exit 0, remote dispatch, binary-identical output and
a nonzero input transfer, the test that would have caught this release
defect.  Proposed for virtu2: the root QA e2e leg for the six skipped
tests (own docker network, real IPs, CAP_SYS_CHROOT on the test container
only) and a clang leg inside the native e2e suite.

## Farm plumbing notes (why no true remote compile ran on H2 either)

For the record, the H2 local-farm attempts (not needed for the regression
tests, but noted for whoever brings one up): `icecc-create-env` is not
built by the plain `make` targets (it is generated from
`client/icecc-create-env.in` only after configure, and must be copied out
separately); the environment tarball creation dies with a `mv` to `//`
(empty env-dir variable in the child); a root-started iceccd exits 1
silently when it cannot chown the env dir to the icecc user (EPERM under
the capng drop, no log line because the log is not open yet); and `-u`
takes a username, not a uid (usage error: "-u requires a valid username").

## Remaining open items

- ~~The daemon-side closer identity~~ **CLOSED (2026-10-05, live capture on
  the worker node)**: the closer is the fd-hygiene sweep's `proc_fallback`
  backend itself.  Verified live: strace -f -k of a real remote compile
  (debug container joining the node's PID namespace, CAP_SYS_PTRACE,
  seccomp=unconfined; one clang-21 TU, 226ms) shows the job child, right
  after fork, `openat("/proc/self/fd")=17`, `close(17)`, then
  `close(0)`, `close(1)`, `close(2)`, ... -- `proc_fallback`'s inventory
  loop, which enumerated EVERY fd (no lower bound) and closed the std
  slots; workit's `pipe(sock_err)` then landed exactly on `(1,2)`.
  Parent-side frames symbolized against the production binary (not
  stripped): `Daemon::handle_old_request` -> `Daemon::answer_client_
  requests` -> `handle_connection` (the fork site).
  WHY the fallback ran at all: the node image is built with glibc-2.27-era
  headers where `SYS_close_range` is NOT DEFINED, so `close_range_sweep`
  compiles to a stub returning `BackendUnavailable` and `proc_fallback`
  is the ONLY backend that ever runs -- verified against the shipped
  binary: zero close_range syscall references.  (close_range itself works
  fine in that container: a static probe of syscall 436 returns 0.)
  The close_range backend starts at `kFirstNonstandardFd` BY CONSTRUCTION;
  the proc backend did not -- that asymmetry is the entire bug.
  **Fix (8d7a8468)**: bound the proc inventory at `kFirstNonstandardFd`
  (`validate_keep_set` already rejects keep fds below 3, so nothing
  legitimate can sit there), plus the three-layer defence above already
  covers the job child even when the sweep backend is swapped.  Regression
  test: `test_proc_fallback_keeps_std_fds` in
  `unittests/p50_fork_fd_hygiene_test.cpp` forces the proc backend via
  `TestHooks::force_close_range_unsupported` (the exact path a
  header-old build takes) and asserts the child's std fds survive the
  sweep while the residue fd is closed -- RED (bound reverted) exits 1
  with "proc_fallback swept a standard fd", GREEN exits 0.
- ~~Loud failure for env installs~~ DONE, then RECONSIDERED: the chardev
  check is now a NAMED WARNING and the install proceeds (see commit 3).
  Rationale: with the std-fd fix a `/dev/null`-less chroot no longer breaks
  the compiler (nothing execs with std fds closed), and a uid-dropped node
  can never mknod -- failing the install would reject every dev-carrying
  env on every sorbet node for no gain.  The warning keeps the missing
  device from ever being SILENT again; stock tolerated libarchive's
  mknod WARNING without a word.

## The QA rounds themselves found pre-existing harness defects (all fixed in the QA commit)

Running the new e2e gate for the first time surfaced six defects in the
test/QA harness itself, all pre-existing at c8bb615f and all previously
invisible because these paths SKIPped in every official run:

- remoteice-quick/p50assignment-remote: the scheduler records a daemon by
  the TCP PEER address of its connection, so daemons connecting via
  `-s 127.0.0.1` register as the loopback sentinel and a strict all-P50
  client correctly REFUSES that UseCS -- the strict row could not run in
  a container at all until ICECC_TEST_SCHED_ADDR existed.
- Both rows derived their scheduler port from their own pid; two pids a
  multiple of 9000 apart land on the SAME port, and under the e2e stage's
  -j2 the two schedulers raced one bind (round 3: port 28479).  Probe-bind
  plus a disjoint strict-row range fixed it -- and the round-5 recurrence
  (port 28520-class, worker "Address already in use" for its whole
  budget) was a SECOND port bug: the scheduler owns sched+1 as its text
  endpoint, and the worker had been seeded exactly there.
- The forced-proc tree was never setcap'd (only the main build was), so
  its cap-less worker downgraded to --no-remote and the cache
  advertisement stayed absent BY DESIGN -- the compilee2e READY gate
  failed every round, deterministically, while every standalone
  reproduction (caps present) passed.  Root-caused by stripping the caps
  on a known-good tree: rc=1 every time.
- The knob compiled close_range out of the TEST binary too, so the
  hygiene suite's injected-failure cases could not reach the backend they
  assert on ("close_range failure was not explicit"); the hooks binary
  is now exempt (the macro is never defined in the daemon).
- `make -C unittests check` cannot build `../cache/check_LIBRARIES` or
  `client/check_PROGRAMS` (recursive-check-only targets); the stages now
  run top-level checks.
- statewritertest flaked ONCE (round 6, "records are intact, whole and in
  order" under -j2) and never again: 400 contended instances (K=8 plus
  CPU hogs in an --cpus 8 container) of the untouched-by-this-series
  binary are all clean, and the product path's per-record offset resume
  reads correct on inspection.  Non-reproducing one-off; noted here so
  a future recurrence is recognisable, NOT fixed by anything here.

## Semantic-interaction review (auto-merged regions)

1. transfer_in_flight at K>1 (FIXED, 9efe08f4): 4c releases the per-route transfer
   lock at write_done (cache/p50_cache_service.cpp:3141-3146), so a successor's
   transfer_bytes() overlaps the head's still-running one on the SAME
   P50ZstdSourceSender. The scalar bool would be cleared by whichever frame exits
   first, so P50CRouteOwner::reset_f_store_exact (client/p50_route_owner.cpp:264)
   could erase the sender mid-transfer. Counter now: any-count semantics. At K=1
   unchanged (0/1).
   What reset_f_store_exact does when a successor is in flight: refuses (returns
   false -> caller sets replacement_required_ = true -> whole-sidecar replacement).
   Same as the pre-pipelining behavior for a head in flight; now also covers the
   overlapped successor.

2. transfer_source_on_owner (cache/p50_cache_service.cpp):
   - 4c write-complete lock release (3141) vs route_replacement_required_ (2937):
     the next call for the same route checks route_replacement_required_ at entry
     (2937) BEFORE acquiring the lane lock (2894) and before the overlapped head's
     coroutine may have stored replacement_required (3032/3043/3077). Interaction:
     a successor admitted during the head's post-write tail can pass the 2937
     check while the head is about to mark replacement_required. NOT a correctness
     hole: the successor's own transfer coroutine will observe whatever terminal
     condition the head hit (poison/epoch are endpoint-side, per-TX statuses are
     per-TX), and the K=1 behavior is identical (the same race exists between two
     sequential calls today, just narrower). The sticky flag is checked again by
     every later call; no torn state is possible because route_replacement_required_
     is a plain atomic store, never cleared here.
   - vs lcbudget (armed admission, client-side): each transfer_source_on_owner call
     takes its own ArmedAdmission::Wait (2812) on the lane's armed window and its
     own Lane::transfer mutex (2894). With pipeline_depth>1 lane_count is forced to
     1 (2529-2537), so head+successor share lane 0: two armed slots, one released
     early by 4c. Armed window slots per lane = armed_window_slots() (8 default);
     the window accounting matches: armed slot released only at Wait destruction
     (function return, after result.get()), so a K=2 route holds 2 armed slots for
     the duration of 2 overlapped transfers - exactly the budget the design doc's
     "(a) armed_window_slots()" clamp assumes. No interaction with the early lock
     release: the lock and the armed slot are separate resources.
   - discard_route/discard path from bind_route_endpoint_identity (3020) inside the
     successor coroutine: runs on the owner executor while the HEAD transfer of the
     same sender is still in flight -> transfer_in_flight() true -> reset_f_store_exact
     refuses -> replacement_required_ (3023 observed.replacement_required). Safe.

3. F-side reaper / collect_input_garbage vs successor connections:
   - The input_backing_reaper (3696, submit_backing_graveyard 2660) only frees
     InputBackingBatch buffers off-thread; it never touches Route, parked waiters,
     or namespace maps. No interaction with parked successor connections.
   - collect_input_garbage (5961) releases closed input-record jobs; the route
     cursor and route.parked are untouched (garbage is input-record-scoped, not
     route-scoped). A parked successor wakes from release_parked_at(route.next_rel)
     at the predecessor's commit (3661) - unaffected by GC of older inputs.
   - evict_namespace_inputs (2669): evicts input records only, route stays. A parked
     successor is safe (its release trigger is the live route).
   - evict_whole_namespace (2695): releases_all_parked first (2706) then erases the
     namespace - the parked successor re-runs the live path and finds the namespace
     gone. Correct ordering.
   - HISTORY_RESET (3283): release_all_parked on the OLD route before wholesale
     Route replacement - no stranded waiter. Correct ordering.
   - reset_store (5879): clears namespaces WITHOUT releasing parked waiters. Parked
     waiters hold shared_ptr<ParkedWaiter> (loop-local) + weak_ptr<ServerIoState>,
     so no dangling pointer - but they would sleep forever (nothing calls
     socket.cancel() on them). Callers today are tests/ops only, always between
     dialogues. OPEN QUESTION for sorbet-main: should reset_store bulk-release
     parked waiters for robustness? Not a merge regression (pre-existing exposure,
     parked waiters only exist at K>1 which is test-gated).

4. discard_route vs the successor window:
   - reset_f_store_exact iterates owners_ (per relationship), and the endpoint's
     successor window (impl_->successors) lives on P50ClientEndpoint, not the
     authority. discard_route erases the authority's Entries for the dead route key;
     the successor coroutine mid-dialogue holds PreparedTuHandle -> but the only
     production path to discard_route (bind_route_endpoint_identity) is refused
     whenever ANY transfer of that relationship's sender is in flight (see 1).
     After both transfers end non-Committed (orphaned handles), discard_route erases
     them + clears the deque + one abandon_active; the endpoint's own
     reset_after_pipeline_poison (4998) then clears impl_->successors + epoch. The
     two structures never diverge: both are cleared uniformly.
   - The poisoned flag (4262-4268 head-deviation path) is endpoint-side; the
     authority-side abandon_route + endpoint reset are called by the bridge
     (client/p50_zstd_sender.cpp) in the same order the k2 tests replicate.
